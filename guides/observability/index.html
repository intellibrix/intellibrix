Observability and durability

Events

Section titled “Events”

Every run emits two streams of events. Both are optional callbacks on Intelligence (as a default) or on a single ask.

onEvent carries the loop’s own LoopEvents: step-start, step-finish, tool-call-start, tool-call-approval-required, tool-call-denied, tool-call-finish, loop-finish and error.

onRunEvent carries structural RunEvents, which are the better fit for logging and tracing:

Event Fields (besides runId)
run:start, run:finish brickName, steps (finish)
model:start, model:finish stepIndex, model, durationMs (finish)
tool:call toolCallId, toolName, input
tool:result toolCallId, toolName, output, durationMs
tool:error toolCallId, toolName, error
approval:requested, approval:resolved toolName, input, trust, decision

Bricks and Structures also have an events emitter for application events such as webhooks.

Tokens and cost

Section titled “Tokens and cost”

Every Intelligence, Brick and Structure has a usage accumulator. A Brick’s usage rolls up into its Structure’s, so you get per-agent and grand totals.

cost comes from a price table keyed by "provider:model". defaultPriceTable is a starting point that goes stale, so pass your own with the priceTable option. If a model is missing from the table, cost is undefined rather than a wrong number.

Record and replay

Section titled “Record and replay”

Record real model calls once, then replay them in tests with no network and no cost.

Fixtures hold the request (tools reduced to name and description) and the model’s answer. Replay returns them in order and throws fixtures exhausted if your code makes more calls than were recorded, so drift fails loudly. Recorded prompts can contain secrets, so review fixtures before you commit them. For hand-written scripts see Testing agents.

Checkpoints and resuming

Section titled “Checkpoints and resuming”

The loop saves its state to a Checkpointer before each step and after each batch of tool results. By default that is InMemoryCheckpointer, which does not survive a restart. To resume after a crash, give the Intelligence a durable one and pass the same runId:

Then call runAgentLoop({ ..., runId, checkpointer, resume: true }). The run restarts from the saved messages and step. A step interrupted midway runs again, so a tool with side effects can run twice. Make such tools idempotent. This is a deliberately small seam, not a workflow engine: back it with Temporal, Inngest or a database if you need retries and exactly-once semantics.
